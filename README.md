# Summary

Исправлено 9 функциональных багов, включая неработающий сценарий стресс-теста из README.

Профилирование показало, что узкое место — **скриптовая логика** (84–90% main thread в WebGL), а не рендеринг (2–3%) и не GC. Основные результаты:

| Метрика | До | После | Δ |
|---|---:|---:|---:|
| GC Alloc, KB/кадр (WebGL) | 10.71 | 4.82 | **−55%** |
| GC collections за 30 с | 36 | 14 | **−61%** |
| Build size on-wire | 10.19 MB | 6.71 MB | **−34%** |
| Cold load, Fast 4G | 10.1 s | 7.9 s | **−22%** |
| Frame time, S2 (бой) | 37.10 ms | 33.29 ms | −10% |
| Frame time, S1 (покой) | 29.67 ms | 32.62 ms | +10% |

Среднее время кадра значимо не изменилось (см. Measurements). Это измеренный результат, а не ожидаемый: аллокации были реальной проблемой, но не главным потребителем CPU.

# Environment

**Unity version:** 6000.4.11f1, Built-in RP, IL2CPP, WebGL.
ТЗ предполагает 6000.5.3f1. Все замеры «до» и «после» сделаны в одной версии, поэтому относительные показатели корректны; абсолютный build size на 6000.5 может отличаться.

**Browser:** Chrome, DevTools Performance, **CPU throttling 6×**. Без троттлинга игра упирается в `requestAnimationFrame` (ровно 16.6 ms, все перцентили совпадают) и разница между сборками неизмерима.

**Hardware:** Windows 11, десктоп. Замеры при закрытом Unity Editor и фоновых приложениях.

**Сценарии измерения** (окно 30 с после набора 140 врагов, Stress Mode):
- **S1** — игрок неподвижен, огонь не ведётся.
- **S2** — игрок перемещается и непрерывно стреляет.

**Инструментарий:**
- `BaselineProbe.cs` — самописный HUD на `ProfilerRecorder`: frame time avg/median/p95/p99/max, GC alloc, число сборок, счётчик врагов. Работает в релизном WebGL, где Unity Profiler недоступен.
- Unity Profiler + Deep Profile — поиск причин (иерархия вызовов, счётчики Calls).
- Chrome DevTools Performance / Network.
- `serve_webgl.py` — локальный сервер с корректными `Content-Encoding: gzip/br`; флаг `--no-store` для cold-замеров.
- `build_report.ps1` — инвентаризация билда, распакованный размер `.gz` из gzip-трейлера.

# Issues Found

**Функциональные:**

1. **Stress Mode не работал через инспектор.** `GameManager.Awake` вызывает `EnableStressMode()` (cap = 140), после чего `EnemySpawner.Start` безусловно выполняет `cap = normalCap` и сбрасывает лимит на 55. Сценарий стресс-теста, описанный в README, был доступен только через F8. Затрагивает сам предмет задания.
2. **Счёт переносился между попытками.** `accumulatedScore` объявлен `static` и переживал перезагрузку сцены.
3. **Подписка на статические `GameEvents` без отписки.** `OnEnable` без парного `OnDisable`: при каждом рестарте добавлялся новый обработчик, старые продолжали висеть, удерживая уничтоженный `GameManager`. Утечка + двойное начисление очков после второго рестарта.
4. **Игрок не умирал при 0 HP.** Условие `CurrentHealth < 0` вместо `<= 0`. HP также уходило в отрицательные значения и отображалось в HUD.
5. **Многократный `RaisePlayerDied`.** При 140 врагах несколько атак приходят в одном кадре — событие смерти отправлялось столько раз, сколько было ударов.
6. **Двойной урон от снаряда.** `Destroy(gameObject)` откладывается до конца кадра, `OnTriggerEnter` успевал сработать повторно.
7. **`Resources.Load<GameObject>("Effects/Impact")` в `OnTriggerEnter`.** Папки `Resources` в проекте нет — вызов выполнялся на каждое попадание и всегда возвращал `null`, молча уходя в fallback-ссылку.
8. **`NullReferenceException` при каждом открытии меню настроек.** `SettingsUI.OnEnable` обращается к `saveService` без проверки; `SaveService` и `AudioManager` создаются в Bootstrap с `DontDestroyOnLoad` и не могут быть назначены через инспектор сцены меню.
9. **Проверка препятствий не срабатывала.** `Physics.Raycast` в `EnemyController` не давал попаданий: `obstructionMask` не настроена, геометрия препятствий не пересекала луч. Код выполнялся 140 раз в кадр и всегда возвращал `false`.

**Производительность:**

10. **`EnemyManager.Update` — самый дорогой мусор в проекте.** Каждый кадр: `enemies.Where(...).OrderBy(...).ToList()` — замыкание, делегат, два итератора, три временных массива, новый `List`. ~5.4 KB/кадр при 140 врагах. Результат использовался, чтобы вызвать `EnemyController.Tick()`, **тело которого пустое**. Дублировал уже работающий `EnemyController.Update`.
11. **Избыточные обращения к Transform.** Deep Profile при 140 врагах: `Component.get_transform` — **691 вызов/кадр**, `Transform.get_position` — **968**. Каждое обращение — переход managed→native, в WebGL дороже, чем в нативной сборке. Занимало больше времени, чем `Physics.Raycast`.
12. **Отсутствие пулов.** `Instantiate`/`Destroy` для снарядов (8/с), эффектов попадания, врагов (8/с в стрессе) и эффектов смерти.
13. **HUD пересобирал строки каждый кадр.** `"HP: " + health` × 4 поля × 60 fps — боксинг и новая строка на каждое обновление.
14. **`new WaitForSeconds` в цикле корутины спавна** — новый объект на каждую итерацию.
15. **`FindObjectOfType` в горячих путях.** В `GameManager.OnPlayerDied` — дважды подряд для одного и того же объекта.

## Что дало наибольший эффект

1. **Кэширование Transform в `EnemyController`** — единственное изменение, давшее измеримый выигрыш по CPU (Deep Profile: −60% времени метода).
2. **Настройки билда** — −34% размера и −22% времени холодной загрузки при нулевом риске для геймплея.
3. **Удаление `EnemyManager` и пулы** — −55% аллокаций и −61% сборок GC.

## Что эффекта не дало и почему это важно

Пулы объектов и удаление LINQ **снизили аллокации вдвое, но не сдвинули среднее время кадра**. Отдельный замер после внедрения пулов дал изменение в пределах 1%.

Вывод, подтверждённый профилем DevTools: при Scripting = 90% и Rendering = 2% узким местом была не сборка мусора, а объём вычислительной работы в `Update` 140 врагов. GC давал спайки (max −8%), но не среднюю нагрузку.

Это причина, по которой я не стал делать широкий рефакторинг «по здравому смыслу»: три из четырёх интуитивно очевидных оптимизаций дали нулевой прирост по CPU, и без замеров это было бы неочевидно.

## Оговорки к измерениям

Честности ради:

- **Frame time значимо не изменился.** В S1 результат на 10% хуже, в S2 на 10% лучше — это в пределах разброса. Заявлять улучшение времени кадра по этим данным нельзя.
- **Геометрия препятствий изменена только на рабочей ветке** (п. 11). Это отличие уровня между сравниваемыми сборками.
- **GC Alloc в редакторе (21.30 KB/кадр) включает overhead редактора.** Deep Profile показал, что игровой код при 140 врагах аллоцирует ~94 B/кадр, а 1.9 KB из 2.0 KB давал `RenderPlayModeViewCameras`. Editor-метрика пригодна только как относительная; абсолютные значения взяты из WebGL.
- **Вклад отдельных настроек билда не разделён** — Stripping, Exceptions и Brotli применены одним шагом, измерен суммарный эффект.

# Remaining Issues

**Оставлено сознательно:**

- **Враги двигаются через `transform.position`, а не `Rigidbody.MovePosition`.** Это телепорт мимо физики: коллизии не разрешаются корректно, враги вдавливаются друг в друга и в игрока. Перевод на `MovePosition` в `FixedUpdate` — правильное решение, но он меняет ощущение движения и требует перенастройки скоростей, что выходит за рамки «минимальных изменений».
- **Скучивание врагов.** Следствие предыдущего пункта. Требует либо физического разделения, либо steering-логики — то есть изменения геймплея.
- **Панель настроек нефункциональна.** Тоглов музыки и звука в сцене нет. Устранён `NullReferenceException`; добавление UI-функционала — новая фича, а не исправление.
- **Рендеринг не оптимизировался.** SetPass 15–18, 2–3% main thread. Оптимизация света, теней и материалов изменила бы визуал без измеримой пользы.
- **`GameObject.FindGameObjectWithTag` в `EnemyController.Update`** при `target == null`. Выполняется один раз за жизнь объекта, в профиле не проявляется.

**Известные ограничения:**

- Прореживание Raycast (п. 12) — единственное изменение, влияющее на поведение: враг до 4 кадров (~66 ms) использует устаревший результат проверки видимости. Интервал вынесен в инспектор.
- Работа велась на Unity 6000.4.11f1 вместо 6000.5.3f1.

# What I Would Do Next

1. **Перевести движение врагов на `Rigidbody.MovePosition` в `FixedUpdate`** — устранит корневую причину скучивания и некорректных коллизий. Требует замера отдельно: фиксированный timestep под нагрузкой ведёт себя иначе, чем `Update`, и в WebGL может дать регресс вместо выигрыша.
2. **Профилировать WebGL с символами.** В релизном `.wasm` имена функций стёрты (`wasm-function[64255]`), и Bottom-up в DevTools нечитаем. Сборка с Debug Symbols дала бы точную атрибуцию оставшихся 84% Scripting.
3. **Снизить нагрузку от 140 `Update`.** Варианты: обновление дальних врагов с меньшей частотой, batched-обработка через `Job System`, либо `Physics.RaycastNonAlloc` пачками. Требует замера каждого варианта.
4. **Разделить вклад настроек билда** — пошагово измерить Stripping, Exceptions и Brotli, чтобы понимать цену каждой.
5. **Сократить `.data` (1.7 MB).** Аудит текстур: сжатие, размеры, mipmaps. Даст дополнительное сокращение cold load.
6. **Переснять полный набор замеров** с идентичными настройками vSync и одинаковой геометрией сцены на обеих ветках.
